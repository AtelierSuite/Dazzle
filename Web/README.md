# Dazzle for the web

The offline, installable web version of Dazzle: the same Swift engine the Apple apps use (`../Engine`), and the same editing code (`../Common/Editing`), compiled to WebAssembly, behind a web interface built on the Atelier design system in Dazzle's orange. No Node packages: the build is Swift and a shell script, and the page is plain HTML, CSS and JavaScript modules. It follows Libretto's and Tables' web apps file for file.

- [PLAN.md](PLAN.md): the porting plan and where it stands.
- [design/](design/): the design system. Rules are in `design/DESIGN.md`.

## Layout

| Folder | What's in it |
| --- | --- |
| `index.html`, `manifest.webmanifest`, `sw.js` | The page, the install manifest and the offline service worker |
| `audience.html` | The slideshow's audience window, opened by the presenter view |
| `app/` | The window: slides, canvas, navigator, inspector, slideshow, files, autosave, strings |
| `engine/` | The engine's WebAssembly interface (Swift), its WASI host, worker and loader (JavaScript), and smoke tests |
| `strings/` | The web app's own string catalogue (`.xcstrings`, five languages); everything else comes from the Apple apps' catalogues |
| `design/` | Design tokens, components, menus, lint and specimen |
| `build/`, `dist/` | Generated by `build.sh`, not checked in: the build, and the site to publish |
| `deploy/`, `wrangler.jsonc` | Publishing to Cloudflare: headers, `robots.txt`, sitemap, the CI build |

## Setting up

The engine builds with the open-source Swift toolchain and its Swift SDK for WebAssembly, of exactly the same version. Xcode's own toolchain can't use the SDK.

1. Install the swift.org toolchain, for example Swift 6.4.2 from [swift.org/install](https://www.swift.org/install/). On a Mac it installs to `~/Library/Developer/Toolchains`.
2. Install the matching Swift SDK for WebAssembly:

   ```sh
   swift sdk install https://download.swift.org/swift-6.4.2-release/wasm-sdk/swift-6.4.2-RELEASE/swift-6.4.2-RELEASE_wasm.artifactbundle.tar.gz \
       --checksum 83baca83553f8c443cda7b84800912e6e709c3acd2e7ebf277794ca5836c0da5
   ```

`build.sh` looks for these at their default locations; set `SWIFT_TOOLCHAIN` and `SWIFT_SDK` to use others.

## Building and running

```sh
./build.sh                # engine, strings and offline file list, into build/
./build.sh --skip-engine  # after changing only the page's own files
npm run serve             # http://localhost:8000 (the specimen is at /design/)
npm test                  # engine smoke tests; pass .pptx/.key paths to open them too
npm run lint:design       # design rules
```

On `localhost` the offline service worker only installs when the address has `?offline`, so that edits show up without a rebuild. Anywhere else it always installs. On `localhost` the window is also `window.dazzle` in the console.

## Deploying

The app is published at [dazzle.atelier.ktgk.app](https://dazzle.atelier.ktgk.app) as a Cloudflare Worker that serves only static files (`wrangler.jsonc`). The custom domain is created by the first deploy.

- `build.sh` assembles the site into `dist/`: just the files the page uses, plus `deploy/_headers`. The engine goes up gzipped (`build/dazzle-engine.bin`, about 20 MB; not named `.gz`, which Cloudflare answers with a bot challenge) because Cloudflare serves files of at most 25 MiB; the worker decompresses it. `build.sh` stops if any file is too large.
- Every push to `main` that touches `Web/`, `Engine/` or `Common/` builds, tests and deploys through `.github/workflows/web.yml`. Pull requests are built and tested only. The workflow runs `deploy/ci-build.sh`, which installs Swift and its SDK for WebAssembly, builds the site and runs the engine smoke tests. The workflow needs the repository secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`.
- To deploy by hand from a Mac: `./build.sh && npx wrangler deploy`. Wrangler is only the deploy tool, not part of the app.

Visitors pick up a new build the next time they open the app: the service worker downloads it alongside the old one when the menu bar's Update button is pressed, and the page reloads into it.

## How it fits together

- **Engine.** `engine/swift/Sources/DazzleWasm` links `Engine/DazzleEngine` (the model and the PowerPoint and Keynote formats; its Core Graphics and Core Text drawing is Apple-only) into a WebAssembly reactor that exports a few C functions. Requests and responses are JSON, with file contents passed as raw bytes alongside.
- **Editing.** `Shared/` links the Apple apps' own editing code from `Common/Editing` (`EditorState` and its extensions), so every change the web app makes (inserting, arranging, formatting, tables, charts, animations, comments, header and footer, slide size, pasting) is made by the same code the iPhone, iPad and Mac apps run. `WebSession.swift` adds what UIKit and AppKit give the Apple apps: undo and redo as snapshots of the presentation, and the file it came from. `Bridge.swift` turns the page's requests into those calls.
- **Drawing.** `WebRenderer.swift` makes the decisions `SlideRenderer`, `TextRenderer` and `ChartRenderer` make (inheritance from layouts and masters, theme colours, fills and outlines, preset geometry, bullets and numbering, autofit, tables, charts) and describes each slide as a scene. `app/slide.js` draws a scene as SVG for outlines and pictures and HTML for text, so the browser sets the type. Preset shapes are the engine's own outlines, written as SVG paths by a portable stand-in for `CGPath` (`Engine/DazzleEngine/Portable/PathStandIn.swift`).
- **Canvas.** `app/canvas.js` puts the slide being edited on screen with its selection: shapes are moved, resized and turned with handles and snapping, picked with a rubber band, and typed into in place. What was typed is read back as paragraphs of runs naming the runs they came from, so formatting the page can't show survives.
- **Slideshow.** `app/slideshow.js` steps through slides and their animations as `PresentationSession` does on Apple platforms, asking the engine for each frame of an animation (`AnimationTimeline.frame`). See below.
- **Files.** Presentations open and save through the File System Access API where the browser has it, and through a file picker and downloads elsewhere. Keynote documents are saved back as Keynote. Open presentations are autosaved to the browser's private storage, so closing the window loses nothing; Open Recent lists them. PDF export prints each slide on a page of its own.

## The slideshow across two windows

With more than one display (`screen.isExtended`), Play opens the slideshow as Keynote and PowerPoint do on a Mac: the audience sees the slide on the other display, and this window becomes the presenter view, with the current and next slides, the notes, the clock and the elapsed time.

- **The audience window** is a separate page, `audience.html`, opened with `window.open()` as a popup. It has no engine: the presenter's window sends it each slide's scene, the pictures and movies on it as `Blob`s, the presentation's embedded fonts, and every frame of every animation, over `postMessage`. It sends back the keys and clicks it receives, so a clicker aimed at either window runs the show. Closing either window ends the show; the presenter's window closes the audience window when it goes away.
- **Placing it on the other display** uses the Window Management API (Chrome and Edge). Once the site is allowed to see the displays, the popup opens over the whole of the other display, asking for the `fullscreen` window feature too, which opens it full screen where the browser supports fullscreen popups (Chromium has offered them to sites with that permission) and is ignored where it doesn't. The browser asks for the permission the first time the presenter presses Move to Other Display; it isn't asked for when the show starts, because the prompt would outlast the click and the popup could no longer open.
- **Going full screen.** A page can only go full screen in answer to a click in it, and opening the popup uses up the click that started the show. So when the browser didn't open it full screen, the presenter view's Fill Screen button posts the audience window a message with `delegate: "fullscreen"` (Capability Delegation, in Chromium), which lets it go full screen on the strength of the presenter's click; and where delegation isn't supported, the audience window shows a Fill Screen button of its own, and a click or the F key there does it.
- **One display, or no popups.** The slideshow plays full screen in this window, and Play › Play in This Window always does. If the browser blocks the popup, the show plays here and says how to allow it.

In Safari and Firefox, which have neither the Window Management API nor fullscreen popups, the audience window opens as an ordinary popup to drag to the projector, and a click on it fills that screen.
